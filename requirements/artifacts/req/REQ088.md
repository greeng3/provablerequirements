The serve backend lets the operator admit a requirement's formalization and then write its provenance back onto the subject's source from the web surface, the way `provreq draft --admit` and `provreq draft --writeback` do from the command line. These are the two draft actions the earlier surfaces deliberately left out: admission carries a human confirmation, and write-back is the only draft action that mutates the subject's own files.

Admitting re-runs the mechanical gate as the source of truth and derives the review tier from it: a clean candidate is optional-review and admits directly, while a vacuity-flagged candidate is mandatory-review and admits only when the operator confirms the read-back. The read surface already renders that deterministic read-back and the admission provenance, so the web surface shows the operator what they are confirming before they confirm it. A candidate that does not gate, or a draft with no candidate, is refused rather than admitted, and admitting records the reviewer against the requirement's current revision.

Writing back requires an admitted draft and refuses a drifted one — an admission made against prose that has since changed must be re-confirmed before it can be written. The write-back stamps the confirmed formalization's provenance onto the subject item through the same source adapter the command line uses, mutating the working tree for the operator to review and commit; the backend never commits on the operator's behalf.

Both actions go through the same admit and write-back machinery the command line uses, so the web surface and the command line never diverge on what may be admitted or written back. On success the backend returns the item's refreshed formalization detail, so the surface reconciles against the tool's authoritative state. With this surface the web UI reaches every draft action the command line offers, completing the formalization half of CLI/UI parity.
