The living loop (REQ039) detects when a stored verdict has drifted — its requirement prose, its
subject code, or the tool moved since the verdict was produced — and marks each affected item as
stale. But drift, detected per item, was never tallied: a verified result that drifted simply
dropped out of the `verified` count, so the operator saw the number fall with no signal of how
much re-verification was owed or which items owed it.

The coverage funnel reports a `stale` count: requirements with a stored verdict that is no longer
fresh, of any polarity. A drifted `holds` has left `verified`; a drifted `fails` is a refutation
that no longer applies — both owe a re-run, and both are counted. A fresh verdict, whether it
holds or fails, is a current answer and is never counted as stale. The count aggregates the
per-item freshness the living loop already computes, giving the operator the loop's actionable
output — how much verified knowledge has gone stale — as a single number rather than markers to
hunt for row by row.

A count alone, though, answers only half of what was missing: it says how much is owed and never
which items owe it. Any surface reporting the count therefore also names the drifted requirements
and, for each, the axes that moved — because the instruction the count carries is to re-verify a
named requirement, and a surface that withholds the name asks the operator to guess it. On a
backlog of any size that is not a smaller job than the one the count was meant to replace; it is
the same hunt, one level up. The listing and the count are read from the same per-item freshness,
so they can never disagree about which requirements are owed.
