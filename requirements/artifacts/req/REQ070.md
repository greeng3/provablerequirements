A checker states one fact in more than one phrasing — by version, by code path, by the shape of
the construct that triggered it. A reader that recognises one phrasing has not partially
understood the output, because the phrasings it does not know do not fall out as "unrecognised":
they fall through to whatever broader pattern happens to match, and are reported as a different
kind of failure, with a confident explanation, at the moment the operator is most likely to act
on it. The sharpest measured case is a checker's own refusal reaching the operator as their code
failing to compile, when the code compiled perfectly.

Where the tool recognises a class of checker output and reports on it, the recognition covers
every phrasing the checker is known to emit for that class, each matched against the checker's
real output rather than a paraphrase of it. An output outside every known phrasing reaches the
operator as unrecognised output — the existing honest floor — never as a member of some other
class whose pattern matches more broadly. A specific recognition takes precedence over a generic
one, and where one run carries several diagnostics, the checker's own first diagnostic decides
what kind of failure the run was: a diagnostic appearing later in the same output must not
preempt the one the operator can act on.

The set of phrasings is the checker's to grow, so this completeness is a maintained property
rather than a one-time achievement. When a new phrasing of a recognised class is found — usually
by a live run, since a passing suite only exercises the phrasings someone already knew — it joins
the recognition together with a fixture of the checker's real output. This requirement exists
because the same defect was fixed three separate times in this codebase before being named; its
purpose is to make the fourth instance a test-and-fixture change rather than a diagnosis.
