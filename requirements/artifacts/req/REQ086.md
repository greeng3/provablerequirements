The serve backend lets the operator author and shape a requirement's formalization from the web surface, the way the mechanical `provreq draft` actions do from the command line — the ones that touch only companion draft state, with no model call and no write to the subject's own source. The operator can set (or replace) the candidate PRL, re-run the mechanical gate on it, attach a grounding binding, and discard the draft entirely.

Setting a candidate runs the gate and records its outcome, re-baselines the draft against the item's current revision, and — because changing the formal claim invalidates any prior confirmation — resets admission to pending and clears grounding bindings, exactly as the command line does. Re-checking updates only the recorded gate outcome. Grounding attaches a binding for a symbol the requirement's vocabulary actually admits, and a symbol the vocabulary does not admit is rejected rather than silently written. Discarding removes the draft. A write against an item the subject does not contain is reported as not found, and one against a subject that has not been adopted is the same unadopted condition the read surface uses. On success the backend returns the item's refreshed formalization detail, so the surface reconciles against the tool's authoritative state.

These writes go through the same source-agnostic draft machinery the command line uses, so the web surface and the command line never diverge on a requirement's candidate, gate, or grounding. Forward-translation by a model and the admit/writeback pair are separate surfaces and are not part of this one.
