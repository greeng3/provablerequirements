The serve backend lets the operator ask the configured model to forward-translate a requirement's prose into a candidate PRL from the web surface, the way `provreq draft --translate` does from the command line. The backend runs the same generate-then-repair loop: the model proposes a candidate, the mechanical gate parses and checks it, and a rejected candidate is fed back for a bounded number of repair rounds. The final candidate is stored with its gate outcome either way — a still-failing candidate is kept with its errors visible so the operator can hand-edit and re-check.

This translation goes through the same source-agnostic translate machinery the command line uses, so the web surface and the command line never diverge on how a candidate is proposed or gated. Setting the translated candidate re-baselines the draft against the item's current revision and resets admission and grounding exactly as authoring a candidate by hand does, because it changes the formal claim.

Forward-translation has no offline fallback: unlike triage, whose prose floor is an honest classification without a model, a translation without a model is not a formalization. When no model is configured, the backend reports an honest error that names the configuration to set, rather than inventing a candidate. A translation request against an item the subject does not contain is reported as not found, and one against a subject that has not been adopted is the same unadopted condition the read surface uses. On success the backend returns the item's refreshed formalization detail, so the surface reconciles against the tool's authoritative state. The admit and writeback pair remains a separate surface and is not part of this one.
