Grounding is the surface where an operator confirms that a binding says what they meant. A
mistake that grounding could have named, and does not, is not thereby prevented — it is deferred
to whatever runs next, and reaches the operator as that stage's failure rather than as the
binding error it is. A compiler message inside an inconclusive verdict is a poor way to learn
that two names were bound to each other by mistake.

The mistake in question is a disagreement between the requirement and the subject about what a
predicate is applied to. A quantified claim ranges its variable over a sort, that sort is bound
to a type in the subject, and the predicate applied to that variable is bound to something in the
subject that takes a parameter of its own written type. Where those two types differ, one of the
two bindings is wrong, and both are already known at the moment the binding is checked.

Grounding therefore compares them and parks the requirement when they disagree, naming both
sides. The comparison is of written names, the same syntactic limit every other check on this
surface works under, and the read-back says so — an alias for the expected type would read as a
mismatch here, and the operator is told that rather than left to infer it.

The check must not park a binding it cannot honestly speak for. Where the requirement does not
determine what a parameter's argument ranges over, where the subject's parameter has no single
written name to compare, or where the two sides could only be reconciled by resolving types
rather than reading them, nothing is claimed and the binding stands on its other checks. A false
park costs the operator a working binding, which is a worse failure than the one this removes.

There is a second disagreement this surface must catch, and it is not between the requirement and
the subject but between the subject and what the tool can write. A predicate is called by
generating a call to it, and the tool writes a reference argument one way only. A parameter
written as a reference to a reference, or as a mutable borrow, cannot be passed by the call it
would generate; and nothing else on this surface notices, because reading a written type through
its references leaves the same name on both sides, so the type comparison agrees.

Where that is so the requirement parks, naming how the parameter is written and where. It would
otherwise ground, and the operator would meet the same fact as a compiler error inside a verdict
that decided nothing — the failure this surface exists to move earlier, occurring in the surface
itself. That this yields an honest inconclusive rather than a wrong answer is not a defense: the
written parameter was in front of the tool at the moment the binding was checked.

This one is reported differently, because it is not the operator's mistake. Their binding may be
exactly right; the limit is the tool's, and the message says so and names the shape it can accept,
rather than implying something needs correcting. Where a binding is wrong *and* the shape is
unwritable, the wrong binding is reported first, since that is the one they can act on.

The same applies where the sort itself did not resolve. What the requirement offers is the name
an operator wrote for a domain, and a name is not an established type until it has been found in
the subject; comparing a predicate's parameter against a name that turned out to be nothing tests
the parameter against a type that does not exist. The failure this produces is not a wrong
verdict — the requirement is ungrounded either way, and correctly so — but a second reason,
naming a second binding, for a single mistake. That reason accuses the predicate binding, which
may be entirely correct, and the operator is sent to inspect something that needs no change while
the true reason waits behind it. One mistake earns one reason, stated where the mistake is.
